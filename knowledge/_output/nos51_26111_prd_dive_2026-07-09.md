## Imaging Product Workflow

This workflow is the reusable operating model for camera / gallery / imaging feature work. It is based on the NOS5.1 26111 pass, where requirements, PRDs, design direction, and technical feasibility all changed after a design review.

### 1. Inputs

Every imaging product cycle should start by collecting the real source materials before changing Jira or PRDs.

| Input | Purpose | Owner / Source | Required handling |
| --- | --- | --- | --- |
| Meeting notes | Capture latest scope, priority, decision changes, open questions, and action items | PM / design / dev meeting | Convert into requirement deltas, not raw prose |
| Requirement Base | Single working table for scope, priority, owner, PRD, Jira, design need, and schedule | PM | Use stable requirement names; do not add temporary codes |
| PRD docs | Product truth for behavior, scope, dependencies, acceptance, and metrics | PM / feature owner | Audit against latest meeting decisions |
| Figma | Design truth for interaction, layout, component behavior, and visual direction | Design | Each software/design requirement should have a page or section |
| Prototype / local reference | Interaction validation, previous project logic, reusable design/engineering model | PM / design / local repo | Reuse proven project assets before rewriting |
| Technical story / feasibility | Dev decomposition, risk, estimate, dependency, and implementation boundary | App / HAL / Tuning / system teams | Mark pending until confirmed; do not block requirement split |
| Jira | Execution tracking after requirement and PRD structure are stable | PM / TPM / dev | Create or map after scope split is clear |

### 2. Intake And Scope Freeze

Goal: turn messy updates into a controlled working scope.

Steps:
- Resolve the correct Base view and use it as the working set.
- Compare the latest meeting notes with the current requirement table.
- Identify added, removed, merged, split, and deferred items.
- Keep parent rows for umbrella initiatives, but create child rows for execution units.
- Mark inherited or non-core items outside the current MP0 view unless they are explicitly retained.
- Record schedule constraints directly in the working doc.

For NOS5.1:
- 2026-07-15 is the formal PRD cutoff.
- 2026-07-31 is the MP0 design draft cutoff.
- Technical stories can remain pending while product/design split continues.

### 4. Split Rules

Split requirements when one parent item contains multiple design surfaces, technical owners, or delivery risks.

| Parent type | Split by | Example |
| --- | --- | --- |
| Layout redesign | Entry, navigation, panel, ratio, motion, visual material | Preset 入口位置, 模式栏下移, 设置面板优化, 16:9 布局 |
| Style / effects | IA, filter, tuning, palette, preset save, recommendation | Style 入口, 滤镜合并, 调色盘模式扩展, Preset 保存 |
| Professional controls | UI baseline, visualization, metering, focus, timer, shutter | 专业模式 UI, 直方图, 峰值对焦, 测光方式 |
| Video controls | Toggle, parameter control, recording behavior, lock rule | EIS 开关, 锁白平衡, Pro Control, 录制中调参 |
| Dual-view / multi-camera | Entry, window behavior, save mode, recording-time switch | 小窗尺寸, 双文件保存, 主副互换 |
| High-resolution mode | Entry, specification choice, onboarding, compatibility | 规格选择入口, 首次弹窗引导 |

Do not split purely for administrative neatness. Split only when it helps design, PRD, owner assignment, cost estimation, feasibility review, or schedule negotiation.

### 5. Cost Tagging

Use a lightweight product cost tag before engineering estimates are available.

| Cost tag | Meaning | Typical examples |
| --- | --- | --- |
| S | Small interaction or copy / entry adjustment | Prompt animation, first-time guide, simple toggle |
| M | Medium UI and state logic, limited cross-mode impact | Preset entry relocation, 16:9 adjustment, Pro Control entry |
| L | Large IA / multi-mode / pipeline or persistence work | Mode bar restructure, Style filter merge, manual exposure |
| M/L | Unclear until technical feasibility returns | Gaussian blur, recording-time controls, dual-file save |

Cost tags are not dev estimates. They are product planning signals for priority and design sequencing.

### 6. PRD Audit Workflow

Every P0 / P1 row with design or technical dependency should go through a PRD audit.

Audit states:

| State | Meaning | Action |
| --- | --- | --- |
| OK | PRD matches current scope | Link it in Base and move to design/dev planning |
| Needs update | PRD exists but misses new meeting decision | Patch sections and acceptance |
| Needs split | PRD contains multiple executable chunks | Add child matrix or child PRDs |
| Conflict | PRD contradicts latest decision | Mark old decision as superseded or re-confirm |
| No PRD | Requirement exists without PRD | Create or link owner draft |
| No permission | PRD exists but cannot be read | Ask owner to grant access before readiness |
| Duplicate / overlap | Two rows describe same behavior | Merge, split boundary, or mark relationship |

PRD review checklist:
- Problem statement matches the latest product goal.
- Scope includes and excludes are current.
- User flow covers default path, edge path, and recovery path.
- Design dependency is explicit.
- Technical dependency is explicit.
- Compatibility is covered across modes, ratios, lenses, and projects.
- Acceptance criteria are testable.
- Metrics and events are named or marked TBD.

### 7. Design Workflow

Design work should start from the split requirement table, not from a single large PRD.

Steps:
- Create or update one Figma page per software/design requirement or tightly coupled group.
- Keep page names stable and code-free.
- Put PRD URL, priority, owner, design date, and dev dependency at the top of each page.
- Align child pages to the cover visual style.
- For parent initiatives, keep an overview page that shows structure and dependency.
- For technical-pending items, still prepare the design intent but mark feasibility as pending.

Design-ready criteria:
- Interaction entry and exit are clear.
- State changes are visible.
- Empty, first-use, default, disabled, and conflict states are covered.
- Layout is checked for core ratios and orientations.
- Visual material decisions are separated from technical feasibility.
- Dependencies are visible enough for dev review.

### 8. Technical Story Workflow

Technical stories can come after the product/design split, but they must eventually close all pending labels.

For each child row, dev should return:
- Feasibility: yes / no / partial / needs experiment.
- Owner: App / HAL / Tuning / system / controls.
- Risk: performance, power, pipeline, compatibility, schedule, UX fallback.
- Estimate or size.
- Dependency.
- Fallback plan.
- Whether it needs separate Jira.

Typical imaging technical questions:
- Does the change affect preview, capture, post-processing, or all three?
- Is it App-only, HAL-dependent, Tuning-dependent, or system-control dependent?
- Does it run during live camera preview?
- Does it affect power or frame rate?
- Does it work across Photo, Video, Portrait, Pro, Dual-View, and High-Resolution?
- Does it change saved media metadata or gallery behavior?
- Does it interact with Filter, Tuning, Image Tone, HDR, Night, Motion Photo, or Preset?

### 9. Priority Workflow

Priority should be decided after child split, not at the umbrella level only.

P0:
- Core MP0 structure or flagship promise.
- Blocks design system or main interaction.
- Required for launch story.
- Must be available for 2026-07-31 design draft if design-dependent.

P1:
- Valuable but can be staged.
- Has feasibility risk.
- Improves the experience but does not block the main structure.
- Can be designed now and implemented after MP0 if needed.

P2:
- Branding polish, optional enhancement, or later iteration.
- Keep visible, but do not let it consume MP0 design capacity.

### 10. Jira Workflow

Jira comes after the structure is stable.

Do not create Jira for every brainstormed detail. Create or map Jira when:
- Requirement row is stable.
- PRD or parent PRD link is known.
- Owner is known or can be assigned.
- Priority is accepted.
- Technical story is at least roughly scoped.

Jira mapping rules:
- Parent row can keep umbrella Jira.
- Child rows can stay without Jira until dev confirms implementation split.
- If one child row has separate owner or schedule, create separate Jira.
- If multiple child rows are design-only under one implementation, keep one Jira and cross-reference child rows in description.

### 11. Acceptance And Validation

Each requirement should move through these gates:

| Gate | Requirement |
| --- | --- |
| Scope ready | Base row has stable name, priority, description, project, domain, source |
| PRD ready | PRD exists, readable, current, and linked |
| Design ready | Figma page exists and covers key states |
| Tech ready | Technical story closed or risk accepted |
| Jira ready | Execution task mapped with owner and schedule |
| Dev ready | Dependencies, APIs, states, and fallback agreed |
| Test ready | Acceptance criteria and compatibility matrix are clear |
| Launch ready | Metrics, regression, known limitations, and release notes are ready |

### 12. Imaging-Specific Compatibility Matrix

Every feature that touches camera UX or imaging output should be checked against this matrix.

| Dimension | Check |
| --- | --- |
| Mode | Photo, Video, Portrait, Night, Pro, High-Resolution, Dual-View |
| Lens | Front, ultra-wide, wide, tele, SAT path |
| Ratio | 4:3, 1:1, 16:9, fullscreen if applicable |
| Recording state | Before recording, during recording, paused, after recording |
| Pipeline | Preview, capture, processing, encode, save, gallery playback |
| Effect stack | Image Tone, Filter, Tuning, Palette, HDR, Night, Beauty, Watermark |
| Persistence | Session memory, cross-session memory, preset save, reset behavior |
| Performance | Preview fps, capture latency, power, thermal, memory |
| Fallback | Unsupported mode, disabled state, old project, missing config |
