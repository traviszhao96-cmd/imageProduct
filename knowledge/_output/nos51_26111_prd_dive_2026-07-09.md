#### AI Preset Algorithm Logic From Local LUT Research

Local sources checked:
- `/Users/travis.zhao/scene-lut-product-package-20260615-143715`
- `/Users/travis.zhao/Desktop/AIPreset`
- `/Users/travis.zhao/scene-lut-product-package-20260615-143715/product_docs/scene-lut-recommendation-logic-20260701.md`
- `/Users/travis.zhao/scene-lut-product-package-20260615-143715/scene_lut_recommend/rules.json`
- `/Users/travis.zhao/Desktop/AIPreset/backend/app/core/semantic_recommender.py`

Current practical algorithm model:

| Layer | Current logic | Product meaning for AI Preset |
| --- | --- | --- |
| Input | Preview frame / still image plus optional metadata | Use the current camera scene when user opens Preset panel |
| Scene recognition | Google ML Kit default Image Labeling, using stable `ImageLabel.index` and `confidence` | Good enough for coarse scene buckets; not a generative model |
| Scene rules | `rules.json` maps ML Kit labels into product `sceneId` with `minConfidence`, `weight`, and `priority` | Product can tune scene definitions without changing algorithm code |
| Scene set | 18 parent scenes: portrait, food, sunset, night, forest, beach, street/vehicle, architecture, sky, pet, flower, auto, mountain, lake/river, waterfall, snow, document, indoor | AI Preset should describe these as recommendation scenes, not as visible mode names |
| Sub-scenes | 29 refinements, using ML Kit, face metadata, EXIF / Lux / CCT / ADRC, tags, and filename signals | Sub-scenes should influence recommendation rank or filter attributes, not become separate UI entries |
| Candidate generation | Top scene matches merge their `recommendations`, dedupe, then keep up to 5 candidates | Algorithm can produce 5 candidates even if UI only shows 3 |
| UI selection | Current rating tool promotes 3 from 5 with stable randomization and falls back if all are low-rated / missing | For Camera product, prefer stable top 3 per Preset panel open; avoid visible random jumping |
| Apply action | User taps a recommended card; no auto-apply | Matches current AI Preset product boundary |
| Fallback | Unknown scene fallback uses safe general presets such as portrait soft / natural / texture | No error state; recommendation area should always have something usable |

Recommended production behavior for the current Preset panel:

1. On every Preset panel open, request or reuse the latest scene-recognition result.
2. Algorithm may maintain up to 5 ranked candidates internally.
3. UI displays the first 3 recommended Presets at the beginning of the Preset strip.
4. If scene recognition is stale or still running, show last valid recommendation first, then update softly when the new result is ready.
5. If no scene hits, use safe fallback Presets instead of showing an empty or error state.
6. Do not auto-apply. User must tap a recommended Preset.
7. Do not create a separate AI Preset entry. Recommendation lives inside the Preset panel.
8. MP0 does not use large-model / cloud-model recommendation because runtime compute is not available.

Scoring logic to document in PRD:

```text
label_score = confidence * weight
scene_score = metadata_match + tag_match + sum(label_score) + label_group_score
scene_order = sort(scene_score desc, priority desc).take(3)
candidate_presets = unique(scene_order.flatMap(scene.recommendations)).take(5)
display_presets = candidate_presets.take(3)
```

Current rule details:
- Metadata strong match can override normal ML Kit scoring.
- Tag / path match is used for sample library and product debugging, but production camera should mainly rely on live scene labels and camera metadata.
- `labelGroups` can model compound scenes, such as portrait with clothing / pose / leisure signals.
- Cafe is currently merged into Indoor; Party / Concert / Event / Fireworks are merged into Night / Neon.
- Current config has `labelThreshold = 0.55`, `detectIntervalMs = 2500`, `maxRecommendations = 5`.

Out-of-MP0 research direction from `AIPreset`:
- Qwen / vision model can generate richer semantic profile: scene type, mood, lighting, risk flags.
- It can re-rank LUT candidates with style tags and diversify top-k via a simple MMR-like strategy.
- It can also optimize tuning parameters with risk-aware constraints for exposure, contrast, saturation, vignette, and grain.
- This is useful as algorithm pre-research only. MP0 product wording should explicitly exclude cloud / large-model generation.

PRD implication:
- The MP0 requirement should be written as "scene-based Preset recommendation", not "AI creates a new Preset".
- The PRD should expose the configurable rule objects: scene labels, scene priority, candidate Presets, default fallback, refresh timing, and UI display count.
- The PRD should separate algorithm candidate count from UI display count: algorithm can return 5; Preset panel displays top 3.

## Imaging Product Workflow

This workflow is the reusable operating model for camera / gallery / imaging feature work. It is based on the NOS5.1 26111 pass, where requirements, PRDs, design direction, and technical feasibility all changed after a design review.

### 1. Inputs

Every imaging product cycle should start by collecting the real source materials before changing Jira or PRDs.

| Input | Purpose | Owner / Source | Required handling |
| --- | --- | --- | --- |
| Meeting notes | Capture latest scope, priority, decision changes, open questions, and action items | PM / design / dev meeting | Convert into requirement deltas, not raw prose |
| Requirement Base | Single working table for scope, priority, owner, PRD, Jira, design need, and schedule | PM | Use stable requirement names; do not add temporary codes |
| PRD docs | Product truth for behavior, scope, dependencies, acceptance, and metrics | PM / feature owner | Audit against latest meeting decisions |
| Figma | Design truth for interaction, layout, component behavior, and visual direction | Design | Each software/design requirement should have a page or section |
| Prototype / local reference | Interaction validation, previous project logic, reusable design/engineering model | PM / design / local repo | Reuse proven project assets before rewriting |
| Technical story / feasibility | Dev decomposition, risk, estimate, dependency, and implementation boundary | App / HAL / Tuning / system teams | Mark pending until confirmed; do not block requirement split |
| Jira | Execution tracking after requirement and PRD structure are stable | PM / TPM / dev | Create or map after scope split is clear |

5. If the FL row intentionally merges the RL item into a broader row, is that merge explicitly stated in the FL description?
